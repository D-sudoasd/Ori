# Agent 工作流效率验证

2026-10-05，以 `40df76fbf345afca013f5ccf3032ade2fd2d5851` 为改造前基准。
本次没有更改模型配置；改进作用于 GPT-6 Astra 等 agent 实际调用的
仓库指引、CLI/MCP、来源读取与检查选择，未测量模型本身的 token 或推理速度。

## 真实开销来源

现有 CLI `import` 先解析生成计划，再解析校验。保存计划逐个工作表重放时，
同一 Excel 重开多次。MCP 四个工具不共享解析结果，`inspect` 后 `plan`
又计算样例/范围。旧 agent 指南默认要求“检查→计划→独立校验→执行”，
CI 则对每次 push/PR 固定运行两版本全套、MCP 和打包。

仓库原无 AGENTS.md，上级工作区接手指引要求先读地图及多份项目文档。
现增加项目级路由覆盖固定预读，详细接口按任务查阅。没有发现项目内
固定加载一组 skills 的脚手架，因此未改动用户的全局 skills。

可获得的历史功能轨迹为旧名 `spectra-to-origin` 的
`01a0de28-88a5-7eb0-9fa9-534ad8f80fa8`（2026-09-26）。其命令文本包含
117 次 `Get-Content`，主入口被读取 20 次、exporter 11 次，4 次全仓文件
清单、12 次 `unittest discover`、18 次定向 unittest 和 8 次 PyInstaller。
期间存在真实修复与跨环境验证，不能将全部次数认定为无效重复。可识别的
skill 文件读取只有一次，没有证据支持“每轮固定加载多技能”。10-03 的
Ori 同步轨迹仅 3 次工具调用，其前后 Git 状态检查属于必要验证。

## 可复现回放

使用 Windows、Python 3.13.0、openpyxl 3.1.5、MCP 2.2.0、xlrd 2.0.2。
TSV 含 2,000 行，Excel 含四个各 2,000 行的工作表。每种任务运行五次，
下表时间为中位数；来源读取包含写出前独立核对，工作簿打开计数仅含
来源 BytesIO，转换检查与写出验证均保留。

| 常见任务 | 来源读取 前→后 | 解析 前→后 | 来源工作簿打开 前→后 | 秒 前→后 |
| --- | --- | --- | --- | --- |
| CLI 直接导入 TSV | 3→2 | 2→1 | 0→0 | 0.0974→0.0924 |
| CLI 直接导入四工作表 Excel | 6→2 | 5→1 | 10→2 | 0.7559→0.5235 |
| CLI 执行已保存的四工作表计划 | 5→2 | 4→1 | 8→2 | 0.5503→0.5269 |
| 保留 MCP 四工具流程 | 5→5 | 4→1 | 0→0 | 0.1415→0.1199 |
| MCP 计划→执行 | 3→3 | 2→1 | 0→0 | 0.1049→0.1133 |

四工作表直接导入的来源读取减少 67%、解析减少 80%、本次回放耗时减少
31%。原 MCP 四步改为“含检查摘要的计划→执行”后，工具调用 4→2，来源
读取 5→3，解析 4→1，转换检查 2→1；执行器仍检查最终计划。最后一行
改造前只返回计划，改造后还包含摘要，减少调用不依赖省略类型/样例检查。
所有对应输出的数据表规范化内容 SHA-256 相同，具体计数和摘要见
[机器可读结果](agent-efficiency-results.json)。

计数是 Python 层调用数，不能解释为物理磁盘读取次数。时间包含解析、
计划、校验和 XLSX 写出，不含进程启动、fixture 生成或首次 SDK 导入。
小表的写出占比高，保存计划重放的耗时收益小于解析次数收益；MCP 两步
在本次测量中略慢，但提供了原流程不含的检查摘要。这里测量的是本机
回放结果，不是模型端到端速度。

安装已有项目依赖，在两个 checkout 上使用同一个脚本和解释器：

```powershell
python -m pip install -r requirements-agent.txt
python scripts/benchmark_agent_workflow.py --repo <基准源码目录> --rows 2000 --repeats 5
python scripts/benchmark_agent_workflow.py --rows 2000 --repeats 5
```

脚本在系统临时目录创建任务，退出时清理；结果只输出 JSON，不改变输入
和仓库。每次回放比较计数与数据摘要，并以中位数报告时间。它使用实际
CLI dispatch 和 SDK 注册的 MCP 工具；真实 stdio 传输另由 MCP 测试验证。

## 检查范围与正确性

`scripts/check_changes.py` 与 CI 共用路由。文档改动从固定完整测试链变成
零代码检查；CLI、GUI 等已知模块选择对应接口测试；MCP 专项只启动 SDK
环境；共享来源/计划契约、新模块和未知配置仍走完整路径。本次新增
SourceCache 属于共享契约，实际使用完整检查和新包验证，没有靠跳过测试
取得提速。

当前路由实测：仅 README 改动选中 0 项代码检查；仅 CLI 改动选中 28 项
相关测试、无构建；仅 MCP 改动选中 2 项 SDK 测试、无基础矩阵或构建；
readers 改动仍选择完整测试、MCP 和打包。路由的 Git 差异获取、失败回退
和执行行为由 17 项回归测试覆盖。

回归覆盖内容/选项变更、同大小同 mtime 改写、可变返回对象、失败恢复、
LRU/容量淘汰、超过容量的多工作簿、重复工作表的可变选项隔离、并发操作、
写出前来源变化、未引用的无缓存公式工作表，以及真实 stdio 的两步导入。
独立调用继续核对来源内容，超限时重新读取，不保存跨进程缓存；缓存
容量是估算数据量，不能当作整个进程 RSS 上限。

最终完整检查为 240 项测试，213 项通过，27 项按原有 opt-in 条件跳过。
已构建新包，验证其 CLI 直接 TSV 导入、四工作表保存计划重放，以及真实
打包后台 worker；输出值、缺失值和 Provenance 均保持正确。相关 Python
文件通过 Ruff E4/E7/E9/F 检查。测试进程指定本机 Tcl/Tk 路径，不更改全局
环境或产品配置。交互式 GUI、真实 Origin 与 Python 3.10 未在本次本机
检查中执行；CI 保留 Python 3.10/3.13 矩阵。后续触发条件见
[开发指南](development.md)。
